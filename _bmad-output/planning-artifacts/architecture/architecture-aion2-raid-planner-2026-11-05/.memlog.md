- (constraint) Motif runner en production (lu dans les dépôts voisins) : workflow GitHub Actions sur push main, runs-on self-hosted avec label nas, git reset --hard origin/main dans le clone du NAS, garde-fou migrations, docker compose up -d --build, health-check curl sur le port localhost, concurrency deploy-nas. Dockerfiles existants : builder rust alpine musl, runtime alpine, user non-root. À rompre : le compose d'un autre service en privileged + pid host + socket Docker + bind mounts.
- (direction) Paradigme : monolithe modulaire à noyau pur (hexagonal allégé). Crate domain sans aucune I/O (entités, états, validation, solveur) ; crate server = http -> app -> infra ; SPA React qui ne dépend que du contrat JSON. La frontière domain/server est un crate Cargo séparé pour que l'interdiction d'I/O soit vérifiée à la compilation et non par convention.
- (decision) AD-1 Un seul conteneur, un seul binaire : le binaire Rust sert /api/* et le build Vite embarqué (rust-embed) avec repli index.html pour les routes sans extension ; Dockerfile multi-étapes node -> rust -> runtime ; pas de CORS (même origine). Binds all. Prevents : deux images à durcir, un nginx à mettre à jour, deux blocs Caddy, CORS et origines distinctes.
- (note) Alternatives pesées pour AD-1. (a) Deux conteneurs nginx + backend, motif des autres services : image nginx à suivre, config nginx à durcir, deux ports, deux blocs Caddy, CORS ou proxy nginx, un deuxième healthcheck ; avantage : rebuild front sans recompiler le Rust. (b) Un conteneur, le binaire sert le build embarqué : une image, un port, un bloc Caddy, zéro CORS, une CSP posée par le seul processus qui connaît ses assets ; coût : chaque changement front recompile l'image (le runner le fait, build Rust en cache de dépendances) et le binaire grossit de quelques centaines de Ko. Critère « moins de pièces » : (b).
- (decision) AD-2 SQLite seule : toute persistance via SQLx sur /data/app.db ; pragmas WAL, synchronous NORMAL, foreign_keys ON, busy_timeout ; pool SQLx avec writer sérialisé ; migrations sqlx::migrate! embarquées, forward-only, immuables une fois poussées ; sauvegarde quotidienne VACUUM INTO dans /data/backups (7 conservées) ; rien de persistant hors /data. Binds infra, app, deploy, CAP-7. Prevents : un second service à sécuriser et sauvegarder, partage du PostgreSQL d'un autre service.
- (note) Alternatives pesées pour AD-2. (a) PostgreSQL dédié en conteneur : un mot de passe de plus dans .env, un port, un volume, une image à mettre à jour, pg_dump à organiser, healthcheck et depends_on ; avantage : Vincent le pratique déjà avec SQLx, requêtes identiques à ses autres projets. (b) PostgreSQL partagé d'un autre service : rejeté dès l'intent dump (couplage, une brèche en touche deux). (c) SQLite dans le volume : aucun service, aucun secret, aucun port, sauvegarde = copie d'un fichier, charge visée (≤ 120 membres, dizaines d'événements) dérisoire ; coût : dialecte SQL un peu différent (dates en TEXT, pas de types riches), un seul writer, et tout ce qui touche la base vit dans le même processus (déjà le cas avec AD-1). Critère « moins de pièces » : (c). Passage à PostgreSQL = changer les migrations et le pool, le domaine ne bouge pas.
- (decision) AD-3 Liens porteurs de droits, aucun secret en clair côté serveur [ADOPTED pour le principe]. Quatre secrets 256 bits CSPRNG en base64url (43 car.), préfixes de chemin distincts : /e/<id> public, /o/<secret> organisateur, /j/<secret> candidature directe, /p/<secret> participant ; ADMIN_SECRET de l'environnement par le même mécanisme (absent = routes admin désactivées). Id public = 128 bits aléatoires base64url (22 car.), indevinable car des événements sont « lien seul ». Le serveur stocke SHA-256(secret), cherche par le hash, ne journalise jamais. L'API reçoit le secret uniquement dans l'en-tête X-Link-Secret, jamais en query string ni cookie. GET et HEAD sans effet (déplieurs de liens Discord). Pages des chemins secrets : X-Robots-Tag noindex, aucune métadonnée og. Referrer-Policy no-referrer partout. Navigateur : liens mémorisés en localStorage par événement. Prevents : un handler qui lit un secret dans l'URL, un lien qui agit sur GET, une fuite de base qui donne les droits, un second mécanisme d'identité.
- (assumption) [ASSUMPTION] La SPA laisse le secret dans la barre d'adresse (pas de replaceState) pour que « copier l'URL » suffise à changer d'appareil ; le risque PC partagé est accepté par le forge. Alternative : effacer l'URL après mémorisation et offrir un bouton « copier mon lien ».
- (decision) AD-4 L'événement est l'unique agrégat : event (1..N slots, 0..N candidatures, 0..K groups, bornes par classe) ; états event open -> locked (unlock possible tant qu'un créneau est futur), cancelled terminal, suppression physique par purge ; candidature status pending/accepted/rejected/withdrawn (lien direct = accepted d'office, public = pending), placement après verrouillage starter(group, slot_index)/bench(group)/unplaced, confirmation unasked/asked/confirmed/declined ; l'organisateur possède status et placement, le participant possède le contenu, sa confirmation et son retrait ; retirée ou rejetée = jamais placée ; même Pseudo[SRV] deux fois = autorisé, signalé à l'organisateur, pas de contrainte d'unicité. Prevents : deux modules écrivant la même ligne sans règle, statuts divergents client/serveur, entité campagne séparée.
- (assumption) [ASSUMPTION] Verrouillage au niveau de l'événement (tous les groupes d'un coup), pas par groupe. Plus simple pour l'organisateur et le code ; un verrouillage par groupe se rajoute sans casser le modèle.
- (decision) AD-5 Contrat HTTP JSON unique défini en Rust, reflété en TypeScript : routes sous /api/ ; DTO dans server::http::dto en camelCase ; erreurs application/problem+json (RFC 9457) avec membre code (identifiant stable domaine.cas) et fields ; aucune phrase utilisateur émise par le serveur ; web/src/api/types.ts seul miroir, modifié dans le même commit que le DTO ; rupture = nouveau préfixe /api/v2/. Prevents : une forme d'erreur par handler, snake_case contre camelCase, types TS devinés.
- (assumption) [ASSUMPTION] Types TS maintenus à la main en v1 (un seul fichier, ~15 DTO) ; génération OpenAPI (utoipa + openapi-typescript) différée tant que le contrat tient en un fichier.
- (decision) AD-6 Données de référence en TOML, rechargées sans rebuild, jamais en dur : reference/*.toml versionnés (régions, serveurs avec faction, instances avec taille et durée par défaut, classes avec rôle et bornes par défaut, rôles), libellés fr et en, identifiants stables en anglais ; copiés dans /data/reference/ par le déploiement ; serveur recharge au démarrage et quand le mtime change (scrutation ≤ 60 s) après validation complète, fichier invalide = ancien jeu conservé + erreur journalisée ; copie embarquée dans l'image pour le premier démarrage ; client via GET /api/reference avec ETag, aucune valeur dans le code client ; serveur valide candidatures et événements contre le jeu courant. Prevents : un nom de serveur ou de classe dans un composant ou un match, deux listes divergentes.

- (decision) AD-7 Anti-abus dans l'application, clé = IP visiteur transmise par l'edge : limiteur en mémoire (crate governor, middleware maison) par IP (IPv4 /32, IPv6 /64) lue dans l'en-tête nommé par CLIENT_IP_HEADER, posé et écrasé par le Caddy du VPS ; repli sur l'adresse du pair uniquement si TRUST_CLIENT_IP_HEADER=false (dev) ; quotas par classe de route (création, candidature, autres écritures, lecture) ; disjoncteur global MAX_EVENTS_PER_HOUR et MAX_CANDIDATURES_PER_HOUR -> 503 + Retry-After ; jeton de formulaire HMAC (FORM_TOKEN_SECRET) émis par GET /api/form-token, exigé par les POST de création et de candidature, âge entre MIN_SUBMIT_DELAY_MS (3000) et 1 h ; champ honeypot ; bornes de champs dans domain::validate ; preuve de travail derrière POW_ENABLED (feature cargo pow, altcha-lib-rs) ; IP jamais écrite en base ni journalisée en prod. - (decision) AD-8 Isolation du conteneur [ADOPTED §4] : image FROM scratch avec binaire musl statique ; user 10001:10001 ; read_only ; cap_drop ALL ; no-new-privileges ; tmpfs /tmp ; pids_limit ; mem_limit 256m ; cpus 1.0 ; ports 127.0.0.1:${PORT}:8080 seulement ; réseau bridge dédié ; un volume nommé monté en /data, rien d'autre ; aucun privileged, pid, socket Docker ni bind mount ; healthcheck par la sous-commande healthcheck du binaire (pas de shell ni curl dans l'image) ; variables obligatoires en ${VAR:?} ; .env à côté du compose sur le NAS, ignoré par git, deploy/.env.example sans valeur. Prevents : le motif privilégié d'un autre service, un montage NAS, un port joignable hors localhost.
- (assumption) [ASSUMPTION] Runtime FROM scratch (aucun shell, aucun paquet, aucune CA) plutôt que alpine ou distroless : surface minimale, rien à mettre à jour hors le binaire.
